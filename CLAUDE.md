# Document Store API (working title)

A central store of JSON documents, reached by end users through an HTTP API. A personal
learning project with minimal real usage. Learning API design is a primary goal, so the
API is written by hand rather than generated by a backend-as-a-service.
Simplicity and maintainability come before speed of delivery.

The developer is experienced in enterprise software and has built a Vue 3 + TypeScript app
(CycleLog), so TypeScript, Vitest and the repository pattern are familiar. Cloudflare
Workers, D1/SQLite and hand-built HTTP APIs are new.

The documents are travel itineraries. Trips are created by a travel planner, agent or
arranger, who gives staff and colleagues manager and editor rights on particular trips.
Travellers share one common reader key, delivered by link, and see only what has been
published.

Decisions below come from design discussions on 2026-11-08 and 2026-11-09. Anything
listed under **Open Decisions** is not settled: ask rather than assume.

# Technology Stack

| Concern        | Choice                                                         |
| -------------- | -------------------------------------------------------------- |
| Runtime        | Cloudflare Workers                                             |
| Framework      | Hono (web-standard `Request`/`Response`, portable runtimes)    |
| Database       | Cloudflare D1 (SQLite), accessed only through a Worker binding |
| Language       | TypeScript, `strict: true`                                     |
| Package manager | npm                                                           |
| Validation     | Zod at the HTTP boundary                                       |
| API contract   | OpenAPI, written by hand (spec-first)                          |
| Tests          | Vitest 5 with `@cloudflare/vitest-plugin` (the renamed `vitest-pool-workers`: real Workers runtime, local D1); Hono's `app.request()` for route tests |
| Local dev      | Wrangler (local D1, works offline)                             |
| Migrations     | Numbered SQL files via `wrangler d1 migrations`, kept in git   |
| Lint / format  | ESLint (flat config) + Prettier                                |

Why D1: hard free-plan limits (queries fail, nothing is billed), no idle pausing, free
point-in-time restore (Time Travel), and the access pattern (check a key, fetch one
document by ID) suits SQLite. D1 is the target environment: design for it directly.

## Dependency policy

Keep dependencies to a minimum. Prefer web-platform and Workers built-ins
(`crypto.getRandomValues`, `crypto.subtle`, `crypto.randomUUID`, `Intl`). Before adding a
library, explain why it's needed, the alternatives (including writing it yourself) and its
maintenance cost, then wait for agreement.

## Not allowed

- User accounts, passwords, sessions, cookies or OAuth (the security model is bearer keys)
- Backend-as-a-service auto-generated APIs (Supabase Data API, Firebase rules, etc.)
- Microservices, Kubernetes, ORMs that hide the SQL
- Personal data in any document (see Data Protection)

# Architecture

## Folder structure (proposed, layer-oriented)

```
src/
  routes/        HTTP handlers: parse, validate, authenticate, call the domain, map to responses
  models/        Domain types, validation schemas, pure rules (permissions, versioning, retention)
  repositories/  Repository interfaces and the D1 implementation; the only code that runs SQL
  auth/          Key generation, hashing, authentication middleware
  utils/         Generic helpers with no domain knowledge
migrations/      D1 SQL migrations
scripts/         Admin tasks run by hand (creator keys, key recovery, purging)
```

Ask before adding another top-level folder.

## Rules

- Routes never run SQL. Repositories never know about HTTP.
- Routes depend on a repository **interface**, never on the D1 implementation directly.
- The API's JSON shape is separate from the stored shape. Repositories map between them,
  so a storage change never silently changes the API contract.
- Business rules (permission checks, retention, version numbering) are pure functions in
  `models/` so they're easy to test.
- No module-level mutable state (Workers instances are short-lived and not shared).

# Security Model

Capability-based access: **holding a key is the permission.** There are no users.

## Keys

| Key     | Prefix | Scope            | Allows                                                 |
| ------- | ------ | ---------------- | ------------------------------------------------------ |
| Creator | `ck_`  | The whole system | Creating documents, nothing else                       |
| Reader  | `rk_`  | One document     | Reading its published version, nothing else            |
| Editor  | `ek_`  | One document     | All reader actions, plus drafts, history, new versions, publishing and deleting |
| Manager | `mk_`  | One document     | All editor actions, plus listing, issuing and revoking keys |

- Document keys form a ladder: reader, editor, manager, each including the one before. A
  manager could issue itself any other key, so withholding read or edit would add no security.
- A creator key can't read or edit any document, even ones it created. A leak can only add
  documents, and `documents.created_by` finds what it added.
- Generate keys as secrets, not identifiers: 32 bytes from `crypto.getRandomValues`,
  base64url-encoded, with the prefix above. Never use UUIDs as keys.
- Prefixes only help people recognise a key. Permission always comes from the database row.
- Staff work on particular trips, never whole collections, so all staff keys are per trip.
  Issue one labelled key per person per trip, so someone can be revoked from a trip without
  affecting anyone else.
- A document's ID is public. Keys are sent separately, so a key can be replaced without
  the document's address changing.
- Store only a SHA-256 hash of each key. Not bcrypt/Argon2: those are for low-entropy
  passwords. Keys are shown once, when issued, and can never be retrieved.
- Document keys live in `document_keys` and creator keys in `creator_keys`: their scopes
  differ, so they don't share a table. Both can be labelled. Cap the keys per document.
- Hash the key in the API before querying, so the database never sees a plaintext key.

## Requests

- Keys travel only in `Authorization: Bearer <key>`. Never in the query string or path.
- The travellers' shared link puts the reader key in the URL fragment
  (`/doc/{id}#rk_…`); the client moves it into the header. Fragments never reach the server.
- Never log keys: redact the `Authorization` header and never echo a key in an error.
- Missing, unknown, revoked or expired key and nonexistent document all return the same `401`,
  revealing nothing. A valid document key without enough permission returns `403`. A creator
  key used on a document, or a document key used to create, counts as unknown: `401`.
- No rate limiting at first, by decision (see Hosting And Limits).
- Headers rather than cookies means CSRF doesn't apply. CORS allows any origin (see
  API Design Conventions).

## Revocation

A manager key revokes any other key on its document, targeting the key's public `id`:

```sql
update document_keys
set revoked_at = coalesce(revoked_at, ?1)
where id = ?2 and document_id = ?3;
```

- `coalesce` makes a repeat safe and keeps the original time. Zero rows changed → `404`.
- `document_id = ?3` is essential: it stops a manager key for one document revoking keys
  on another.
- A manager key can't revoke itself (`409 Conflict`), so a document always keeps a working
  manager key. To replace one, issue a new manager key, then use it to revoke the old one.
- Replacing any key = issue a new one, revoke the old one.
- Revocation is immediate, so never cache key lookups. It only stops future access:
  anything already read can't be taken back.
- Key rows are never deleted, except when purging a whole document. Versions keep
  `created_by`, so you can see what a leaked key wrote and restore the last good version.
- Revoking a creator key doesn't affect the documents it made: their keys keep working.

## Expiry

- Creator, reader and editor keys can have an optional `expires_at`. Every key check
  ignores expired keys, so an expired key gets the same `401` as an unknown one.
- **Manager keys never expire** (enforced by a check constraint). Otherwise a document could
  silently lose its last working manager key. Leavers are handled by revocation.
- Expiry is given as a calendar date, `YYYY-MM-DD`, everywhere (API and admin scripts;
  decided 2026-11-10). It is read in UTC and the key works through the whole of that day,
  so `expires_at` stores the first instant of the next day: `2027-12-31` is stored as
  `2028-01-01T00:00:00.000Z`. Responses give the date back as `YYYY-MM-DD`. The rule lives
  in `src/models/expiry.ts`.
- A manager sets expiry when issuing a key or later with `PATCH`, which can't be in the past
  (`422`); today's date is allowed. Keys start with no expiry, so the client sets the shared
  reader key's expiry after creating the trip, some time after it ends.
- Extending a key reactivates it if it has expired, so trip dates can change without
  re-sending the travellers' link. A revoked key can never be reactivated.

## Admin script

Run by hand through `wrangler d1 execute`, adding nothing to the public API:

- Issuing, expiring and revoking creator keys. Nothing sits above them in the API, and the first one
  can't come through the API at all. Generate the key locally and insert only its hash.
  Issuing is `scripts/issue-creator-key.ts`, which requires a label and an explicit
  `--local` or `--remote`. Expiring and revoking are not scripted yet.
- Recovering a document whose manager key is lost, by inserting a replacement key.
- Purging a document or version for good.

## Things that hold the real power

- Access to the Cloudflare account and its API tokens bypasses every key. Never commit
  secrets; use `wrangler secret`.
- Purging is admin-script only, so a leaked manager key can't destroy history for good.

## Rejected for now

- End-to-end encryption with the reader key: loses server-side validation, merge patch and
  queries, and a lost key means lost data. Could return later as a new storage version.

# Data Model

## Immutable versioned snapshots

- Document content is **never updated**. Every change inserts a new full snapshot with the
  next version number. Store full copies, not diffs. This is not event sourcing.
- "Current" is a query (`max(version)` via the primary key), not a pointer row.
- Version numbers increase per document, are never reused and never renumbered.
- Deleting a document inserts a deletion-marker version (`deleted = 1`, `body` null).
  Restoring = posting an old version's body as a new version.
- Keys are ordinary mutable rows: revocation is a security setting, not document history.

## Storage conventions (SQLite)

- IDs: UUID text. Booleans: integer 0/1.
- Timestamps: ISO-8601 UTC text, always from `toISOString()`, so that comparing them as
  strings (as the expiry checks do) gives the right order.
- JSON bodies: text with `check (json_valid(body))`.
- `permission`: text with a check constraint (adding a value is a small migration).
- No JSON indexes until a real query needs one.

## Schema (starting point)

```sql
create table creator_keys (
  id            text primary key,     -- UUID
  key_hash      blob not null unique, -- SHA-256; plaintext never stored
  label         text,                 -- e.g. 'my laptop'
  created_at    text not null,
  last_used_at  text,
  expires_at    text,
  revoked_at    text
);

create table documents (            -- identity only; never changes
  id          text primary key,     -- UUID
  type        text not null,
  created_at  text not null,
  created_by  text not null references creator_keys (id)
);

create index documents_created_by on documents (created_by);

create table document_keys (
  id            text primary key,     -- UUID; referenced instead of the hash
  document_id   text not null references documents (id) on delete cascade,
  key_hash      blob not null unique, -- SHA-256; plaintext never stored
  permission    text not null check (permission in ('reader', 'editor', 'manager')),
  label         text,                 -- e.g. 'phone app'
  created_at    text not null,
  last_used_at  text,                 -- update at most hourly, not on every read
  expires_at    text,
  revoked_at    text,
  check (permission <> 'manager' or expires_at is null)
);

create index document_keys_document_id on document_keys (document_id);

create table document_versions (
  document_id  text not null references documents (id) on delete cascade,
  version      integer not null,
  body         text check (body is null or json_valid(body)),
  deleted      integer not null default 0 check (deleted in (0, 1)),
  created_at   text not null,
  created_by   text references document_keys (id),
  primary key (document_id, version),
  check ((deleted = 0 and body is not null) or (deleted = 1 and body is null))
);

create table document_publications (  -- at most one row per document
  document_id   text primary key references documents (id) on delete cascade,
  version       integer not null,
  published_at  text not null,
  published_by  text references document_keys (id),
  foreign key (document_id, version) references document_versions (document_id, version)
);

create trigger document_versions_are_immutable
before update on document_versions
begin
  select raise(abort, 'document versions are immutable');
end;
```

Deletes on `document_versions` are allowed only for retention pruning and purging. D1 has
no database roles, so this is enforced by the trigger plus a repository with no update
method.

## Indexing

- D1 bills for rows scanned, not rows returned, so every frequent query must use an index.
  Check new queries with `EXPLAIN QUERY PLAN`: `SEARCH … USING INDEX` is what you want, and
  a plain `SCAN` reads every row.
- Primary keys and `unique` columns are indexed automatically. Foreign keys are not.
- Each index adds a written row whenever a write touches the indexed column, and writes are
  the tighter daily limit. Only add an index for a query that runs often.
- `document_versions.created_by` is deliberately not indexed: that would charge every save
  to speed up a rare leak review.
- Log `meta.rows_read` and `meta.rows_written` from D1 results to catch expensive queries.
- Run `PRAGMA optimize` after a migration that creates an index.

## Reading

Each read checks the key and fetches in one query. The published version:

```sql
select k.id as key_id, k.permission, v.version, v.body
from document_keys k
left join document_publications p on p.document_id = k.document_id
left join document_versions v on v.document_id = p.document_id and v.version = p.version
where k.document_id = ?1 and k.key_hash = ?2 and k.revoked_at is null
  and (k.expires_at is null or k.expires_at > ?3);
```

No row → `401`. A row with a null `version` → `404` (nothing is published).

The latest working version (the history endpoints follow the same key rules):

```sql
select v.version, v.body, v.deleted, k.id as key_id, k.permission
from document_versions v
join document_keys k on k.document_id = v.document_id
where v.document_id = ?1 and k.key_hash = ?2 and k.revoked_at is null
  and (k.expires_at is null or k.expires_at > ?3)
order by v.version desc
limit 1;
```

No row → `401`. A reader key → `403`.

## Creating

1. Check the key's shape (`recogniseKey`), hash it and look it up in `creator_keys`,
   ignoring revoked and expired keys, in one query that also counts the key's documents.
   No match → `401`. Authentication comes before any check of the body.
2. Check the body: `415` unless `application/json`, `413` over the size limit (counted while
   reading, not trusted from `Content-Length`), `400` for invalid UTF-8 or JSON, `422`
   unless a JSON object. The request body is the document itself, with no envelope.
3. Check the creator key's cap on documents → `409`. It is a soft cap: simultaneous creates
   can pass it by one or two, which is harmless for a storage limit.
4. Generate the document ID and its first manager, editor and reader keys.
5. In one `batch()`, insert the document, version 1 and the three key rows, and set the
   creator key's `last_used_at`.
6. Return `201` with `{ id, managerKey, editorKey, readerKey }`, shown only this once,
   plus `Location`, `ETag: "1"` and `Cache-Control: no-store`.

A new document starts unpublished, so its reader key gets `404` until someone publishes.

Version 1's `created_by` is null, because that column points at `document_keys`. The creator
is recorded on `documents.created_by`.

## Writing, concurrency and retention

D1 has no interactive transactions: atomicity comes from `batch()`, which runs statements as
one transaction and rolls back if any fails. Write each statement so it is safe whatever
the others do.

A write inserts the next version only if the caller's base version is still the latest,
and prunes versions beyond the newest `MAX_VERSIONS` in the same batch:

```ts
const [inserted] = await db.batch([
  db.prepare(
    `insert into document_versions (document_id, version, body, created_at, created_by)
     select ?1, ?2 + 1, ?3, ?4, ?5
     where (select max(version) from document_versions where document_id = ?1) = ?2`,
  ).bind(id, baseVersion, body, now, keyId),
  db.prepare(
    `delete from document_versions
     where document_id = ?1
       and version <= (select max(version) from document_versions where document_id = ?1) - ?2
       and version not in (select version from document_publications where document_id = ?1)`,
  ).bind(id, MAX_VERSIONS),
]);

if (inserted.meta.changes === 0) {
  // someone else wrote first → 412 Precondition Failed
}
```

- Pruning lives in this repository method, not in a trigger (hidden behaviour) or a
  scheduled job (growth between runs). `MAX_VERSIONS` is configuration, not schema.
- Deletion markers count as versions.

## Publishing

Saving a version never changes what travellers see. An editor publishes one specific
version, so what goes live is exactly what was reviewed, not whatever is newest:

```sql
insert into document_publications (document_id, version, published_at, published_by)
select ?1, ?2, ?3, ?4
where exists (select 1 from document_versions
              where document_id = ?1 and version = ?2 and deleted = 0)
on conflict (document_id) do update set
  version = excluded.version,
  published_at = excluded.published_at,
  published_by = excluded.published_by;
```

- Zero rows changed → `422` (the version doesn't exist, was pruned or is a deletion marker).
- The publication is a mutable setting, like a key. Version content stays immutable.
- Reverting = publishing an earlier retained version. Unpublishing removes the row.
- `DELETE` on a document removes its publication in the same batch as the deletion marker,
  so readers lose access at once. Restoring a document doesn't republish it.
- A reader key can't see drafts, history or deletion markers.
- The document is the security boundary: supplier costs, commission or internal notes can't
  be hidden inside a published version, so they belong in a separate document.

# Retention And Growth

- Keep only the newest `MAX_VERSIONS` versions per document, plus the published version
  if it's older than those. A foreign key stops a published version being deleted.
- Retention bounds growth per document only. Worst case is
  documents × `MAX_VERSIONS` × maximum document size, so growth is controlled by:
  a document size limit and a cap on documents per creator key. These limit storage, not
  request rates, so they apply from the start.
- Limits (decided 2026-11-10, all configuration rather than schema):

  | Setting                     | Value  |
  | --------------------------- | ------ |
  | `MAX_VERSIONS`              | 10     |
  | Maximum document size       | 200 KB (200,000 bytes, as Cloudflare counts), measured on the UTF-8 request body → `413` |
  | Documents per creator key   | 100    |
  | Keys per document           | 20     |
  | Minimum age before pruning  | none   |

  A cap being hit returns `409 Conflict` with its own problem `type` (`403` already means
  "not enough permission"). At 200 KB and 10 versions a document can reach 2 MB, so about
  250 documents could fill D1's 500 MB free database; one creator key's full cap is 200 MB.
  At 200 KB, parsing and validating a body should stay well inside the Workers Free plan's
  10 ms CPU limit per request, but measure it once writes exist.
- Retention lets a leaked editor key flush good history by writing junk versions, and
  nothing throttles that at first. Pruning spares the published version, and D1 Time Travel
  (7 days on the free plan) is the last-resort backstop.
- Deleted documents never get another write, so pruning never reaches them. Later: a
  scheduled job (Cron Trigger) purges documents whose latest version is a deletion marker
  older than a grace period (30 days suggested). Build when deleted data takes real space.
- Time Travel keeps pruned and purged data restorable for 7 days. Deletion is complete
  only after that window.

# API Design

## Endpoints (all under `/v1`)

```
POST    /v1/documents                    create → 201 { id, managerKey, editorKey, readerKey } (shown once)
GET     /v1/documents/{id}/published     what travellers see, ETag: "<version>"; 404 if unpublished
PUT     /v1/documents/{id}/published     publish: { "version": n } → 204
DELETE  /v1/documents/{id}/published     unpublish → 204
GET     /v1/documents/{id}               latest working version, ETag: "<version>"
GET     /v1/documents/{id}/versions      history: numbers, dates, no bodies; includes oldestAvailable
GET     /v1/documents/{id}/versions/{n}  one version; never changes
POST    /v1/documents/{id}/versions      new full version; If-Match: "<version>" → 201 + Location
PATCH   /v1/documents/{id}               JSON Merge Patch (RFC 7396) on latest; stored as a new full version
DELETE  /v1/documents/{id}               inserts a deletion-marker version
GET     /v1/documents/{id}/keys          list: id, permission, label, dates; never the key or hash
POST    /v1/documents/{id}/keys          issue → 201 { id, key, permission, label, expiresAt } (shown once)
PATCH   /v1/documents/{id}/keys/{keyId}  change expiry: { "expiresAt": "YYYY-MM-DD" or null } → 204
DELETE  /v1/documents/{id}/keys/{keyId}  revoke → 204
```

| Operation                                       | Key required              |
| ----------------------------------------------- | ------------------------- |
| Create a document                               | Creator                   |
| Read the published version                      | Reader, editor or manager |
| Read the latest version, history or one version | Editor or manager         |
| New version, `PATCH`, `DELETE` a document       | Editor or manager         |
| Publish or unpublish                            | Editor or manager         |
| List, issue, change expiry of or revoke keys    | Manager                   |
| Creator keys, lost-key recovery, purging        | Admin script (not the API) |

## Conventions

- Errors use Problem Details (RFC 9457), `application/problem+json`, via
  `src/utils/problem.ts`. `type` is `about:blank` when the status says everything, and a
  relative `/problems/<slug>` URI for problems clients must tell apart
  (e.g. `/problems/document-limit-reached`).
- Request and response bodies are the document itself, with no envelope; the version travels
  in `ETag` / `If-Match`.
- Any response that contains a key gets `Cache-Control: no-store`.
- Every `401` is the same response, with `WWW-Authenticate: Bearer`.
- CORS allows any origin (`*`) without credentials: with bearer keys and no cookies it
  protects nothing. Exposed headers: `ETag`, `Location`.
- Writes require `If-Match`. Missing → `428 Precondition Required`. Stale → `412`.
- `GET` latest and `GET` published honour `If-None-Match` → `304`, which suits travellers
  on poor connections. Separate URLs for latest and published, so one URL never returns
  different content depending on the key.
- A specific version is cached with `Cache-Control: private, max-age=31536000, immutable`
  (`private` because responses depend on a key).
- Status codes: `400` malformed request, `422` well-formed but invalid, `401` / `403` as in
  Security Model, `404` for a key not on this document or nothing published, `409 Conflict` for a manager key
  revoking itself or a cap being hit, `410 Gone` for a pruned version or for an editor or
  manager key reading a deleted document (readers get `404`: its publication was removed),
  `413 Content Too Large`, `415 Unsupported Media Type` for a body that isn't JSON,
  `429 Too Many Requests` with `Retry-After` (once throttling is added).
- Retried writes are safe: a retry after a successful-but-timed-out write gets `412`; the
  client fetches the latest version and compares.
- Collections (e.g. history) use cursor-based pagination.
- There is no cross-document listing or search: with no users there is no "my documents".
  There is no agency level or collection of trips, because staff work on particular trips.

# Hosting And Limits

Cloudflare Workers Free + D1, deliberately: going over a limit causes errors, never a bill.
Moving to Workers Paid ($5/month) removes that hard stop, so revisit cost protection first.

D1 limits on the free plan (checked 2026-11-08; verify against developers.cloudflare.com
before relying on them):

| Limit                                  | Free plan                         |
| -------------------------------------- | --------------------------------- |
| Rows read / written                    | 5 million / 100,000 per day       |
| When exceeded                          | Queries fail until 00:00 UTC      |
| Database size                          | 500 MB (5 GB per account)         |
| Row / string / BLOB size               | 2 MB (keep document limit well below) |
| SQL statement length                   | 100 KB                            |
| Bound parameters per query             | 100                               |
| Queries per Worker invocation          | 50 (a `batch()` counts as one)    |
| Time Travel (point-in-time restore)    | 7 days (30 on paid)               |

Each D1 database processes one query at a time; fine at this usage.

## Throttling

Allow high request rates at first; throttle later if it proves necessary. On the free plan
this can't cause a bill or unbounded storage. The accepted risk is availability: a runaway
client or leaked key can use up the daily write allowance, and then every D1 query fails,
for all trips and travellers, until 00:00 UTC. If that happens, add Cloudflare's own rate
limiting, keyed on the document or key rather than the IP address (a whole office or tour
group can share one address). Check what the free plan includes at that point.

# Data Protection

- **Documents never contain personal data**: no traveller names, contact, passport or
  payment details. Never add fields for them. The API can't detect personal data typed into
  free text, so trip document schemas should avoid open-ended text where they can, and the
  planner client should tell staff the rule.
- If throttling is added later, any IP addresses kept for it count as personal data under
  GDPR: keep them only briefly.

# Testing

- Vitest. Put tests next to the code as `*.spec.ts`.
- Unit tests for `models/`: permission rules, retention, version numbering, validation,
  key format.
- Repository tests against a local D1.
- Route tests with `app.request(path, init, env)` against the real local D1 repositories,
  not fakes. Fakes can behave differently from real SQL; add one only if a test needs it.
- Every security boundary has a test: each key can do only what the operations table allows,
  a key for one document doesn't work on another, a revoked key is rejected, unknown document
  and wrong key are indistinguishable, keys never appear in logs or errors.
- Revocation tests: a manager key can't revoke itself (`409`) or a key on another document
  (`404`), repeating a revocation is safe, and a creator key's documents survive its revocation.
- Publishing tests: a reader key gets only the published version and `403` on latest and
  history, saving a version doesn't change what readers see, publishing a pruned version or
  deletion marker → `422`, pruning never removes the published version, `DELETE` removes
  reader access.
- Expiry tests: an expired key gets `401` (on both key tables), a manager key can't be given
  an expiry, extending reactivates an expired key but never a revoked one.
- Concurrency and retention tests: stale `If-Match` → `412`, missing → `428`,
  `MAX_VERSIONS + 1` writes leave `MAX_VERSIONS` versions, a pruned version → `410`.

# Code Quality

- Readability over cleverness. Explicit code over magic. Self-documenting names.
- Small functions with strong types. Avoid `any`; use `unknown` and narrow.
- Commits use the GitHub no-reply email.

# Build Plan

Agreed 2026-11-10. Each step: write its part of `openapi.yaml` first, include the
security-boundary tests that apply to it, pass `npm run check`, then commit. Describe the
design of a step before starting it if it adds an endpoint, a folder or a dependency.

1. **Keys:** generate, hash and recognise keys as pure functions (`src/auth/keys.ts`),
   with unit tests.
2. **Admin script:** issue a creator key (`scripts/`). It prints the key once and inserts
   only its hash with `wrangler d1 execute --command`.
3. **Create a trip:** the repository's creation batch and `POST /v1/documents`, which checks
   the creator key and returns the three keys. Also the HTTP groundwork every later route
   uses: Problem Details errors, body-size limit and Zod validation, authentication
   middleware with `Authorization` redaction, the repository interface passed into the
   app, CORS, and the start of `openapi.yaml`.
4. **Save a version:** `GET /v1/documents/{id}` (latest, with `ETag`) and
   `POST /v1/documents/{id}/versions` with `If-Match`, the conflict check and pruning.
5. **Publish and read:** `PUT …/published` and `GET …/published`, completing the first full
   traveller path.
6. **Keys:** list, issue, change expiry, revoke.
7. **The rest:** history, one version, `PATCH` (merge patch), `DELETE` a document,
   unpublish.

# Open Decisions

Ask before building anything that depends on these.

1. **Key storage in the planner client:** the API can't list a planner's trips or recover
   their keys, so the client needs a keyring of trip IDs, names and keys. A keyring kept in
   one browser doesn't follow someone to another device and can be lost, so decide how it
   is backed up or moved.
2. **Client details:** web, mobile or both, offline copies for travellers, and how the
   planner client handles `412` conflicts between staff.
3. **Document body schema:** the itinerary schema hasn't been designed yet. Until it is
   (decided 2026-11-10), a body is any JSON object (not an array or a single value) within
   the size limit, and `documents.type` is always `'itinerary'`. The real schema will tighten
   this, and should avoid open-ended text (see Data Protection).
4. **Smaller API details:** the history cursor format and page size. (CORS, problem `type`s
   and `creator_keys.last_used_at`, set on every create, were settled in build step 3.)
